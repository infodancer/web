# Security Policy -- errnotice module

## Reporting

Part of the [infodancer/web](../README.md) monorepo. Use
[GitHub's private vulnerability reporting](https://github.com/infodancer/web/security/advisories/new).
Do not open public issues for security problems.

## Security model

`errnotice` records captured HTTP failures into a Postgres `error_notices`
table. Its inputs (request path, panic value, goroutine stack) are
partly attacker-influenced -- a 5xx or panic can be driven by a crafted request
-- so the module treats them as untrusted.

- **SQL is always parameterized.** Every query is generated by sqlc with
  `pgx/v5` and bound positionally; no field is ever concatenated into SQL text.
  The fingerprint, request path, panic value, and stack reach the database only
  as bound parameters, so a hostile path or panic message cannot inject SQL.

- **The fingerprint is a grouping heuristic, not a security boundary.** The
  fingerprint is a sha256 over (component, method, normalized path, status,
  panic class) and only decides which failures are treated as "the same" row. An
  attacker who can drive requests can already cause real failures to be recorded
  -- that is the point. The worst a fingerprint collision can do is merge two
  failure groups or split one; it grants no access and corrupts no data.
  Crucially, the inputs are bound parameters (above), so a chosen-path "collision"
  cannot become a SQL-injection or a write outside the row it keys.

- **Stored stack and panic text are bounded and untrusted.** The goroutine
  stack is truncated to 8 KiB and the panic value to 1 KiB before storage, so a
  hostile or pathological panic cannot bloat a row. The stored text is whatever
  the failing code put in the panic or stack; it is recorded for an operator to
  triage and must be treated as untrusted when later displayed (escape it in any
  admin view -- this module stores, it does not render).

- **No PII or secrets by construction.** The module records only what `obs`
  hands it: component, method, path, status, request id, panic value, and stack.
  It does not read request bodies, headers, cookies, or form fields, so it does
  not pull credentials or personal data into the table. Whether a panic value or
  stack itself leaks a secret is the failing code's concern, not this module's --
  do not panic with secrets in the message. The request id correlates a row to
  the structured log without storing request content.

- **Recording never blocks or breaks the request.** The UPSERT runs on a context
  detached from the request (`context.WithoutCancel` + a 5s timeout) so a
  disconnected client cannot cancel the write, and a write failure is logged at
  ERROR and swallowed -- `Report` never panics or propagates. A failing
  error-recorder cannot take down the request path it observes.

## Known limitations (v0.1)

- Table only: this module records failures; it does not page anyone and does not
  emit a `notify` event. Alerting is a separate, metric-driven, out-of-process
  concern (Prometheus + Alertmanager); the in-app feed is future work.
- The path-normalization heuristic (digits, long hex, UUID segments collapse to
  `:id`) is conservative. A volatile id in an unusual shape (e.g. a short
  base62 token) may not be collapsed, so distinct values produce distinct rows;
  this over-counts groups, it does not lose failures.
