# media — design (v0.1)

## Problem

The portfolio's authoring tools need somewhere to put images. mdedit (the
Markdown editor) can insert an image *reference*; `infodancer/ui/markdown`
decides what `<img>` survives sanitization; neither stores or serves bytes.
blog's DESIGN names "the v0.2 media subsystem" as the piece it waits on for
embedded images. `media` is that piece: a mountable component that accepts an
upload, makes it safe, stores it, and serves it back under a stable URL.

Serving user-uploaded files is a classic stored-XSS and privacy vector (SVG
with script, polyglot files sniffed as HTML, EXIF GPS leakage, decompression
bombs). Concentrating that risk in one audited, tested component — the way
`markdown` concentrates sanitization — is the point.

## Scope

In scope: accept an image upload over HTTP, validate and re-encode it to a
safe canonical form, content-address and store it, and serve it with correct
security headers. A small host integration surface matching the suite mount
contract.

Out of scope (host owns these, via hooks): authentication, authorization, CSRF,
and the rate-limit policy on the public intake. `media` exposes seams for them;
it does not decide who may upload. Also out of scope: SVG, animation, and
non-image media.

Derived sizes (thumbnails) were deferred from v0.1 and added in v0.2 —
pregenerated and autogenerated at upload time; see "Derived sizes" below.

## Decisions

### Home: `github.com/infodancer/web/media`

A nested module in the backend monorepo, next to blog (its first consumer) and
matching the suite's Postgres mount contract (`New`/`NewStore(pool)`, a mounted
`http.Handler`, `Migrate(ctx, pool)` under a dedicated goose table, `media_*`
tables, sqlc + pgx/v5). It is *not* in `infodancer/ui` — that repo is the
front-end visual layer; the store/serve service belongs with the other
backend components.

### Categories: server-side buckets, one handler each

An image is never a free-floating upload. It is always tied to some owning
record (a campaign, a creature, a character) the user may write to, and that
record's *kind* is the **category**. Two rules follow:

- **The category is server-side, never client-set.** It is `Config.Category`,
  fixed when a handler is built — `NewHandler` rejects a missing or invalid one.
  A host registers one handler per category over a single shared store
  ("configure the store once, categories within it"). The category reaches the
  URL only because the host mounts that handler at a category path and points
  `PublicBaseURL` there; the wire never carries it.
- **An upload must be authorized against an existing record.** `Config.Authorize`
  returns the owning record's id (the *subject*, derived server-side from the
  request) and whether the user may write to it; `ok=false` rejects the upload.
  The subject is recorded in metadata, and `Store.ListBySubject` returns a
  record's images.

This gives a degree of logical separation that does not rely on a metadata
column alone: campaign images and creature images are physically apart, on disk
and in the key.

### Byte storage: Postgres `bytea` behind a `BlobStore` seam

Bytes live in Postgres (`bytea`) by default — consistent with the suite's
"Postgres everywhere, host owns one pool" posture, transactional with the
metadata, and backed up with the database. At portfolio scale (personal sites,
session-notes images capped at a few MB) this is fine, and content-addressed
URLs with immutable caching keep origin reads rare.

A `BlobStore` interface isolates byte storage, keyed by `(category, hash)` so
one configured store serves every category and a filesystem or object-store
backend can be added without touching the pipeline or the metadata:

```go
type BlobStore interface {
    Put(ctx context.Context, category, hash, contentType string, data []byte) error
    Get(ctx context.Context, category, hash string) (data []byte, contentType string, err error)
    Has(ctx context.Context, category, hash string) (bool, error)
}
```

Metadata (`media_objects`, keyed `(category, hash)`: content_type, width,
height, byte_size, subject, created_at) is always in Postgres; only the bytes
move when the backend is swapped. Shipped backends:

- `PostgresBlobStore` — bytes in `media_blobs` (default), keyed `(category, hash)`.
- `FilesystemBlobStore` — bytes on disk, content-addressed and category-sharded
  `<root>/<category>/ab/cd/<hash>` with a content-type sidecar and atomic
  (temp-file + rename) writes. This is the same "image files under a root"
  posture osg uses for chronicle images, adapted to the content-addressed
  model; the category (`ValidCategory`) and hash (`looksLikeHash`) are validated
  before any path is built, so traversal is impossible, and bytes are still
  served through the handler (Content-Type + nosniff), never via a bare
  directory listing. An empty category drops the prefix (`<root>/ab/cd/<hash>`).
- `MemoryBlobStore` — in-memory, for tests and no-database dev mounts.

### Transform policy: re-encode raster; reject SVG and animated

Allowed input formats: **PNG, JPEG, GIF, WebP**. Every upload is decoded and
**re-encoded** to a canonical form — **lossless WebP (VP8L) for PNG, static GIF,
and WebP**, and **q85 JPEG for JPEG**. Re-encoding is the strongest available
guarantee: it strips EXIF (including GPS), discards trailing/leading bytes, and
neutralizes polyglots (a file that is both a valid GIF and valid HTML/JS does
not survive a decode→encode round trip).

Why this format split: lossless WebP preserves PNG/GIF/WebP sources (including
alpha) with no generation loss and is smaller than PNG; encoding a *photographic*
JPEG losslessly would only bloat it, so JPEG stays JPEG. WebP encoding is pure Go
([nativewebp](https://github.com/HugoSmits86/nativewebp), VP8L only). A *lossy*
WebP encoder would need cgo + libwebp — a C image library on the untrusted-image
path and a break from the single-static-binary / `FROM scratch` posture — and is
deliberately not used. Consequence: re-encoding an already-lossy WebP losslessly
yields a somewhat larger file, but adds no further loss. Each WebP side is capped
at 16383px (the VP8L bitstream limit), checked from the header before decode.

- **SVG is rejected.** It is XML, not a raster format, so it fails the decode
  gate; there is no safe-by-construction SVG, and a sanitized-SVG path is
  deferred until something needs vector images.
- **Animated GIF is rejected** (detected via multi-frame decode). Static GIF
  re-encodes to lossless WebP. **Animated WebP is rejected** too — the decoder
  does not implement the animated VP8X container, so it fails the decode gate.

### Serving: the module owns the GET handler

`media` serves bytes from its own handler so the security headers live in one
audited place: the stored `Content-Type`, `X-Content-Type-Options: nosniff`
(defeats content sniffing), a long immutable `Cache-Control` and `ETag`
(content-addressed, so the bytes for a URL never change), and
`Content-Disposition: inline`. A configurable public base URL lets a host front
the bytes with a CDN or a separate origin for defense-in-depth.

### Derived sizes (thumbnails) — v0.2

A thumbnail is treated as **just another safe, content-addressed image**, not a
special kind of object. The bytes of each derived size get their own SHA-256 and
are stored in the *same* `BlobStore` under the *same* category as the original,
`(category, thumbHash)`. The consequence that drives the design: **the serve
path needs no change** — `GET {mount}/{thumbHash}` already serves any blob in the
category, with the same `nosniff` + immutable-cache headers. There is no
on-the-fly resize endpoint and no separate thumbnail store.

What gets added is small:

- **Generation is in the pure pipeline.** `Process` decodes the source once and,
  for each `Config.Thumbnails` spec, downscales that decoded image and re-encodes
  it with the *same* format policy as the original (q85 JPEG for a JPEG source,
  lossless WebP otherwise). Downscaling uses `golang.org/x/image/draw`'s
  CatmullRom kernel — pure Go, already a dependency (the WebP decoder), no cgo.
  Each variant is content-addressed like the original. So a library caller that
  never touches the database still gets safe, hashed thumbnails from `Process`.
- **Fit modes, never upscale.** `FitInside` scales down to fit within the box
  with aspect preserved (variable output dims); `FitCover` scales to cover then
  center-crops to exactly the box (uniform grid). Neither enlarges a source
  smaller than the box — cover instead crops to the box aspect ratio at native
  scale. The caller picks per spec.
- **A map table, not a byte store.** `media_variants`, keyed
  `(category, parent_hash, name)`, records each variant's own `hash`,
  content-type, and dimensions. It maps an original to its named sizes; the bytes
  live in the `BlobStore` like any blob, so swapping the byte backend still moves
  only bytes. The upload response gains a `thumbnails` array (omitted when none
  are configured, preserving the existing `![](url)` consumers).
- **Backfill for existing corpora.** `BackfillThumbnails` walks a category
  (keyset-paged by the primary key), regenerates *only the missing* sizes from
  each original's stored canonical bytes, and is idempotent (content-addressed
  blobs + `ON CONFLICT DO NOTHING`). New uploads never need it; it exists for
  adopting the feature on already-stored images or after adding a new size.

Why no lossy WebP for thumbnails (where small size matters most): the same
reason as the original re-encode — a lossy WebP encoder needs cgo + libwebp on
the untrusted-image path, breaking the pure-Go / `FROM scratch` posture. JPEG
sources already produce compact q85 JPEG thumbnails; lossless-WebP thumbnails of
other sources are small because the dimensions are small.

## The security pipeline

One function, pure and Postgres-free, is the heart of the module and the focus
of the test corpus:

```
Process(r io.Reader, cfg Config) (Processed, error)
```

1. **Bound the input.** `io.LimitReader` to `cfg.MaxUploadBytes`; read fully.
   The client's declared content-type and filename are ignored.
2. **Sniff.** Magic-byte detection selects a decoder. Extension and client type
   are never trusted.
3. **Guard dimensions.** `image.DecodeConfig` reads width/height cheaply;
   reject if `width*height > cfg.MaxPixels` *before* a full decode, so a
   decompression bomb (a tiny file declaring 50000×50000) is refused without
   allocating it.
4. **Decode + animation check.** Decode the image; for GIF, a multi-frame
   decode rejects animation.
5. **Re-encode** to the canonical format → strips metadata, kills polyglots.
6. **Content-address.** `hash = sha256(reencoded)`; the hash is the object id
   and the URL slug. Identical uploads dedupe.

`Processed` carries the safe bytes, canonical content-type, width, height, and
hash. The store persists metadata + bytes (via `BlobStore`); the handler maps
HTTP ⇆ pipeline.

## Host integration surface

```go
media.Migrate(ctx, pool)
store := media.NewStore(pool)               // metadata, shared
blobs := media.NewPostgresBlobStore(pool)    // bytes, shared (default)

// One handler per category over the shared store.
h, err := media.NewHandler(store, blobs, media.Config{
    Category:       "campaign",             // fixed, server-side
    MaxUploadBytes: 10 << 20,
    MaxPixels:      25_000_000,
    PublicBaseURL:  "/media/campaign",      // where THIS handler's GET is mounted
    Authorize: func(r *http.Request) (subject string, ok bool) {
        id := r.PathValue("campaign")       // the owning record, from the host route
        return id, host.MayEditCampaign(r, id)
    },
})
mux.Handle("/media/campaign/", http.StripPrefix("/media/campaign", h.Routes()))
```

- `POST {mount}` — multipart field `image`. Runs the pipeline; on success
  `201` + JSON `{ "url": "...", "width": N, "height": N }` (the `url` under this
  handler's `PublicBaseURL`). mdedit's adapter inserts `![](url)`.
- `GET {mount}/{hash}` — serves the bytes (scoped to this handler's category)
  with the headers above.
- `Authorize` gates uploads and names the owning record (host auth); a
  rate-limit hook guards public intake. CSRF on the upload POST is the host's
  responsibility, per the suite conventions (the handler also enforces a
  same-origin guard).

## Testing

A malicious-upload corpus, mirroring `markdown`'s XSS corpus and grown the same
way (new vectors are added, never removed):

- polyglots: GIF/JS, JPEG with appended HTML, PNG with trailing script;
- SVG with `<script>` (rejected);
- animated GIF (rejected);
- decompression bomb: small file, huge declared dimensions (rejected at
  `DecodeConfig`);
- magic/extension mismatch (`.png` that is really JPEG — accepted as JPEG by
  content, never by extension);
- EXIF with GPS (assert stripped from the re-encoded output);
- truncated / zero-byte / non-image (PDF, HTML) — rejected.

The pipeline corpus needs no database. Store and handler get Postgres-backed
tests via testcontainers behind the `integration` build tag, plus an in-memory
`BlobStore` and a fake store interface for fast handler unit tests.

## Versioning

Path-prefixed tags (`media/vX.Y.Z`), pre-1.0. `Config`, `Process`/`Processed`,
`BlobStore`, `NewStore`/`NewHandler`/`Migrate`, and the upload/serve HTTP
contract are the public surface.
